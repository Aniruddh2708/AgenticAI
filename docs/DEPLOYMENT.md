# Deployment and demo delivery

The dashboard is a local, synthetic research demo. The source repository is not a
hosted application. The project includes a container recipe; this does not create a
public website or a hosting account.

## Local container

From the repository root, with Docker installed, first configure a strong secret
`VIBEFINANCE_API_TOKEN` through your shell environment or host secret settings.
The dashboard's access gate asks for this token. Do not commit it to any file.

```sh
docker compose -f deploy/compose.yaml up --build -d
docker compose -f deploy/compose.yaml logs -f
```

Open `http://localhost:8501`. The default Compose mapping only accepts connections
from your own computer. Stop with `docker compose -f deploy/compose.yaml down`;
the named state volume is preserved. Do not add `--volumes` unless you intend to
remove saved demo profiles and history.

The image installs the hashed base lockfile, runs as an unprivileged user, keeps
SQLite under `/data`, and starts both services with the existing launcher. The API
listens on container loopback; only Streamlit's dashboard port is exposed. The
optional live feed and embedding packages are deliberately excluded from this
base offline image.

The offline build and `deploy/check_container.py` were exercised in the cloud
workspace. The check verified dashboard readiness, the non-root runtime, API access
control, the actual browser access gate, a persisted five-agent result and an exact
session surviving a restart. It generates a temporary credential in memory and
removes only its own verification container and test-data volume afterward. The
ordinary online build was attempted but blocked by build-container DNS/proxy access;
its successful path in a different network has not been asserted.

With the image already built and Playwright/HTTPX installed, repeat the check with:

```sh
python deploy/check_container.py
```

## A hosting service

Use a Docker-capable service with persistent disk support and WebSocket proxying.
Point the public service to port 8501, or set `VIBEFINANCE_DASHBOARD_PORT` to the port
assigned by your provider. Mount persistent storage at `/data`; retain
`VIBEFINANCE_STATE_DIR=/data`. Keep `VIBEFINANCE_API_HOST=127.0.0.1` and avoid
publishing API port 8000. The dashboard uses the internal API URL generated by the
launcher.

For a provider that sets `PORT`:

```sh
VIBEFINANCE_DASHBOARD_HOST=0.0.0.0 VIBEFINANCE_DASHBOARD_PORT="$PORT" python -m vibefinance.demo
```

Configure TLS and access restrictions through the host's supported settings.
`VIBEFINANCE_API_TOKEN` is required for an externally bound dashboard. It supplies
a shared dashboard access gate and protects internal API calls; it does not add
individual user accounts or per-investor authorization. This app has shared
seeded profiles and shared history. Publish only synthetic demo data and do not
enter real investor information into a shared demo.

### When the container build cannot use your network proxy

Some managed workspaces permit registry access on the host but do not provide
working DNS/proxy access inside Docker's build container. Download verified
wheels on the host, then use the offline build recipe:

```sh
python3.11 -m pip download --require-hashes --only-binary=:all: --dest .runtime/wheelhouse -r requirements.lock
docker build --build-context verified_wheels=.runtime/wheelhouse -f deploy/Dockerfile.offline -t vibefinance:local .
```

Use a host matching the image's Python 3.11 and Linux architecture; wheels downloaded
on macOS cannot be copied into a Linux image. Artifact hash checks remain enabled
during both download and installation. The base image is pinned by digest. Once
the image has been built, start the existing image without a network rebuild:

```sh
docker compose -f deploy/compose.yaml up -d --no-build
```

No public provider was provisioned by this work. A public URL remains dependent on
your selected service/account, hosting credentials and deployment authorization.

## Optional Yahoo integration check

This integration remains optional. Install the separate pinned requirements into
an isolated environment, then run a strict check:

```sh
python3.11 -m venv .runtime/live-venv
.runtime/live-venv/bin/python -m pip install -r requirements-live.txt
.runtime/live-venv/bin/python scripts/check_live.py --require-live
```

An exit code of 1 means a live download was not established. The script prints the
actual mode and fallback warning. Yahoo requests retain normal TLS verification;
there is no bypass for certificates, network allowlists or provider rate limits.
The live feed being unavailable does not stop the offline demonstration. The
dashboard intentionally stays in simulated mode even if this optional check works.

## Presentation and backup assets

Open `docs/PRESENTATION.html` in a browser. It is a self-contained presentation with
keyboard navigation (left/right), print styles and an explicit disclosure of
synthetic data and uncalibrated recommendation strength. Its evidence slide points
to the executable Metrics view rather than promising unmeasured investment returns.

The capture script requires Playwright, Chromium and FFmpeg:

```sh
python -m pip install playwright==1.62.0
python -m playwright install chromium
python scripts/capture_demo.py --url http://127.0.0.1:8501
```

Alternatively pass an existing browser path with `--chromium /path/to/chromium`.
When recording a protected demo, supply its existing shared credential through
`VIBEFINANCE_API_TOKEN` in the capture process's environment; never pass it in a
command-line argument. The default local demo requires no token.
By default it records the actual running dashboard, visits each tab, demonstrates
comparison, conflict and missing filing, and saves screenshots plus a browser
MP4 video under `.runtime/demo-assets/`. It records actual Chromium screen frames
through the public CDP API and retains their observed timing; the installed system
FFmpeg encodes the result. No screenshot is mocked. The script does not
edit profiles or record user decisions. Its manifest lists which real views were
captured. Recording length defaults to two minutes; use `--duration 0` for a quick
verification run. It is silent automation rather than a narrated rehearsal.

Generated recordings, databases and virtual environments are ignored by Git. Copy
them through the platform's supported artifact export before relying on them
outside this workspace; an internal `/workspace` link is not a public download URL.

The verified delivery also includes a deliberately selected, small set of actual
captures in `docs/assets/`: the eight-page presentation PDF, twelve dashboard
screenshots and a 119.3-second silent MP4 backup. See `docs/assets/README.md` and the
capture manifest for exactly what was recorded. These selected copies are project
deliverables; their ignored runtime originals and intermediate frames are retained
locally. They are not a narrated rehearsal or a public application deployment.
